# DATA_MODEL.md — local data, item identity, progress rules

Source: `docs/BUILD_PLAN.md` section 6. Restated in English for code agents.
When in doubt, the plan wins. Migrations and exact SQL are written in
milestone 2; the status rule is implemented in milestone 6.

## Principles

- All learning history lives on the phone in SQLite (`expo-sqlite`).
- A local `profile_id` (UUID) represents the learner. It is not a remote
  account. All pedagogical data is isolated by profile **and** language.
- UUIDs are generated by application code. Models reference known IDs; they
  never create profiles or primary keys.
- Versioned migrations, foreign keys on, transactional writes, parameterized
  SQL. UI code stays separate from persistence (repositories).
- Counters are **recomputable from events**. The model proposes observations;
  the code validates references and aggregates.

## Tables (proposed)

| Table | Essential fields |
| --- | --- |
| `profiles` | `id`, `support_language='en'`, `selected_language`, `created_at` |
| `lessons` | `id`, `profile_id`, `language`, `title`, `status`, `created_at`, `updated_at` |
| `learning_items` | `id`, `profile_id`, `language`, `kind`, `canonical_form`, `reading`, `meaning_en`, `explanation_en`, `sense_key` |
| `lesson_items` | `lesson_id`, `item_id`, `source_text`, `source_kind`, `review_status`, `position` |
| `sessions` | `id`, `profile_id`, `lesson_id`, `language`, `lesson_snapshot_json`, `status`, `started_at`, `ended_at`, `active_seconds`, `evaluation_status` |
| `messages` | `id`, `session_id`, `role`, `sequence`, `content`, `raw_transcript`, `input_source`, `revision`, `created_at` |
| `learning_events` | `id`, `session_id`, `message_id`, `message_revision`, `item_id`, `event_kind`, `verdict`, `assisted`, `evidence_text`, `evaluator_version`, `valid` |
| `item_progress` | `profile_id`, `item_id`, `times_seen`, `times_used`, `correct_uses`, `incorrect_uses`, `last_seen_at`, `last_error`, `status` |
| `language_progress` | `profile_id`, `language`, `sessions_count`, `total_practice_seconds`, `learner_summary`, `summary_version`, `updated_at` |
| `pending_jobs` | `id`, `session_id`, `job_kind`, `payload_version`, `status`, `attempts`, `last_error` |

Notes:

- One `learning_items` table with `kind = 'vocabulary' | 'grammar'` avoids
  duplicating every operation. `reading` is nullable (pinyin for zh,
  romanization for ko, `null` for fr). Grammar uses `canonical_form` as the
  pattern and `explanation_en` for the explanation.
- `lesson_items.review_status` tracks the human review of each extracted item
  (for example accepted / edited / flagged). `lesson_items` also records which
  items are active for the next session (at most 10 words and 2 patterns);
  the exact column is decided in milestone 2.
- `messages.input_source` records how the user text was produced: spoken
  transcript, edited transcript, typed, or copied from **Help me answer**.
  `revision` increments when a transcript is edited.
- `sessions.lesson_snapshot_json` is an immutable copy of the lesson at session
  start. Editing the lesson later does not change past evidence.
- `pending_jobs` holds post-session evaluation work that must survive an app
  close and resume on the next foreground launch.

## Item identity

Never identify a word by its raw string alone. Identity = language + canonical
form + kind + distinct sense (`sense_key`). Unicode NFC normalization and
whitespace trimming only; never strip accents, tones or script differences.

- Korean and French inflected variants are linked to an existing item only
  with evidence; no uncertain automatic merge.
- The same word in two lessons reuses its progress when the sense is the same.
- A doubtful merge stays a proposal shown in **Review lesson**.
- Do not infer identity from the English translation alone.
- No universal lemmatization algorithm in V1.

## Measured vs estimated

| Signal | Meaning | Nature |
| --- | --- | --- |
| Session ended, active duration, message sent | Observable events | Measured |
| `times_seen` | Item displayed in a tutor message, at most once per item and message. Not "understood". Audio replay does not increment it. | Measured |
| `times_used` | Item used in a user message, at most once per item and message. For inflected forms or grammar the detection may rely on a model estimate. | Measured / estimated |
| `correct_uses`, `incorrect_uses` | Based on an evaluation, not objective truth. Keep exact evidence, message revision and evaluator version. `uncertain` is allowed. | Estimated |
| Assisted / typed answers | Labelled separately (`assisted`, `input_source`). They do not prove spontaneous oral recall. | Measured label |

Active duration excludes time in background.

## Status rule (initial, deliberately conservative)

- `new`: no learner usage.
- `learning`: at least one usage.
- `comfortable`: at least **5 uses judged correct without assistance, spread
  over 3 sessions**, and no `incorrect` verdict among the last 3 evaluable
  attempts.
- A new error moves the item back to `learning`.

These are product heuristics to tune, not a scientific or CEFR scale. Do not
mix typed and oral performance when granting `comfortable` for oral practice:
an edited transcript may count as text practice but not toward the oral
threshold. For recurring difficulties, surface repeated sourced observations;
no fourth `struggling` status. For a grammar item, `times_seen` may stay
undetermined without reliable evidence.

## Idempotence and recovery

- Unique constraint on
  `(session_id, message_id, message_revision, item_id, event_kind)` prevents
  double counting on retry. Re-inserting the same evaluation does not change
  progress.
- Editing a transcript invalidates the observations attached to the old
  revision (`valid = 0` or transactional replacement).
- A new evaluator version must not duplicate old events: transactional
  replacement or explicit revision.
- Repeated session finalization does not increment `sessions_count` twice.
- Evaluation flow: write `pending_jobs` row → call the API → apply
  observations in one transaction → recompute `item_progress` and
  `language_progress` → mark the job done. If the app is closed, resume on the
  next foreground launch; do not rely on JavaScript continuing after close.
- Local deletion cancels pending jobs. Import replaces everything in one
  transaction after validation, then rebuilds aggregates.

## Context sent to the tutor

Priority: system rules → target language → lesson snapshot → recent turns →
session summary → relevant memory. Initial budget: 10 active words, 2
patterns, last 8 messages, summary ≤ 150 words, 5 memory observations. Always
keep the last question and the user's answer.

For a new session, select observations about the active items plus a few
relevant difficulties in the same language. No embeddings. Lesson words have
priority but function words and natural-sentence vocabulary are allowed; do
not force old words in.

## Backup format

Versioned JSON containing lessons, items, sessions, messages, events and
progress for the local profile. No keys or tokens. Replacement import only in
V1, after a fresh backup and explicit confirmation. Validate schema,
references and limits before mutating anything. Details in milestone 7.
